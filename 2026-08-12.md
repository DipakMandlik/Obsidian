Databricks Volumes :

1) What a Volume is

A Databricks Volume is **not** a database table. A table stores structured rows and columns. A Volume stores files and folders.

```
TABLE  → rows + columns   (customer_id | name | status)
VOLUME → files + folders  (loan_agreement.pdf, KYC.pdf, ...)
```

Examples of what belongs in a Volume: PDF, DOCX, PNG, JSON, CSV, audio, video. Databricks recommends Unity Catalog volumes for governing this kind of non-tabular data.

2) Table vs Volume — when to use which

| Requirement            | Use    |
| ---------------------- | ------ |
| Customer records       | Table  |
| Payments               | Table  |
| Transactions           | Table  |
| Program information    | Table  |
| PDF                    | Volume |
| DOCX                   | Volume |
| Image                  | Volume |
| Scanned document       | Volume |
| Audio                  | Volume |
| Video                  | Volume |

For our Databricks use case, Bronze, Silver, and Gold hold tables. PDF documents live in a Volume. The table stores information *about* the document. The Volume stores the actual document.

Think of a bank. Customer records go into tables. Loan agreements, KYC scans, income statements, and credit reports are files — those go into a Volume. You would never shove a 30-page loan agreement into a relational table.

3) Still governed by Unity Catalog

A Volume is not just a bare ADLS folder. It becomes:

```
ADLS → Unity Catalog → Volume
```

Unity Catalog gives you governance around the files: who can access the volume, who can read or write files, which identities can reach it, auditing, and centralized discovery. The privileges involved are `READ VOLUME`, `WRITE VOLUME`, and `USE VOLUME`.

4) Two types of Volumes

```
            VOLUMES
               │
      ┌────────┴────────┐
   MANAGED             EXTERNAL
```

5) Managed Volume

With a Managed Volume, Unity Catalog controls the storage location and lifecycle. You effectively tell Databricks: "I need a governed place to store these files," and Databricks handles the managed storage underneath.

```
Unity Catalog → Managed Volume → Managed Storage → ADLS Gen2
```

You do not need to manually specify the underlying ADLS path when creating the volume. This is a natural fit when Databricks owns the storage end to end — for example an internal HR AI app holding resumes, offer letters, appraisals, and certificates that nobody else needs to reach directly. It is also the fastest route for a quick POC.

6) External Volume

An External Volume means the files already live in a storage location you control outside Databricks' managed lifecycle. Enterprise ADLS is the usual case — contracts, invoices, reports already sitting in a corporate container. You do not want Databricks to move those files.

```
Existing ADLS → Storage Credential → External Location → External Volume → Unity Catalog
```

Databricks uses external volumes specifically to govern existing cloud object storage locations. Important misconception to kill: **External does not mean ungoverned.** The underlying storage is externally managed, but Unity Catalog still governs the volume. Only the ownership of the storage location differs.

7) Managed vs External — decision cheatsheet

| Scenario                                      | Choice   |
| --------------------------------------------- | -------- |
| New Databricks-only documents                 | Managed  |
| Existing enterprise ADLS repository           | External |
| Another application also needs the files      | External |
| POC / quick test                              | Managed  |

The shortest way to remember the difference is ownership. Managed means: "Databricks, manage the storage for this workload." External means: "The enterprise already manages this storage. Databricks should govern and consume it."

8) Three-part access chain (for External)

External volumes need three Unity Catalog objects, each with a different job:

```
Storage Credential  → Who are you? (identity Unity Catalog uses to reach cloud storage)
External Location   → Which storage path are you allowed to access? (abfss://.../documents/)
Volume              → Which governed file area do users and workloads actually use?
```

Office building analogy: Storage Credential is your employee ID badge. External Location is the building or area you are authorized to enter. Volume is the specific filing room you may use. The PDF is the actual document inside that room.

9) Folder structure — one Volume, many clients

For our use case the layout is:

```
ADLS
└── databricks-use-case
    └── documents
        ├── CLIENT_001
        │     ├── financial
        │     ├── legal
        │     ├── compliance
        │     └── supporting
        ├── CLIENT_002
        │     ├── financial
        │     ├── legal
        │     ├── compliance
        │     └── supporting
        └── ...
```

The rule is simple: **1 External Volume → many client folders.** Never create one Volume per client. At 10,000 clients that becomes a governance and administration nightmare. Keep one Volume and treat `client_id` as a metadata and filtering attribute, alongside `document_id`, `document_type`, `document_path`, `document_date`, and `processing_status`.

10) Governed path pattern

Databricks exposes a governed path like `/Volumes/<catalog>/<schema>/<volume>/`. For our setup that becomes:

```
/Volumes/databricks_use_case/documents/client_documents/
/Volumes/databricks_use_case/documents/client_documents/CLIENT_001/
/Volumes/databricks_use_case/documents/client_documents/CLIENT_001/financial/report.pdf
```

Jobs should reference this Volume path, never the raw ADLS URI.

11) Metadata table vs actual document

This distinction matters a lot for AI pipelines. The Volume holds the real file (`agreement.pdf`). A metadata table holds the structured facts about it:

```
document_id = DOC001
client_id   = CLIENT001
document_type = Agreement
document_path = /Volumes/...
status = Processed
```

The metadata table **points to** the actual PDF. Keep them separate so the pipeline can manage documents systematically.

12) Lifecycle difference

Managed lifecycle: Create Volume → Unity Catalog creates/controls storage → upload files → use them → Drop Volume (managed data lifecycle applies).

External lifecycle: ADLS already exists → register External Location → Create External Volume → use files → Drop External Volume. Dropping the External Volume does **not** delete the underlying enterprise ADLS repository. That separation is exactly why External Volumes are useful for existing enterprise document stores.

13) Cost — the most important thing to remember

Do not memorize "Managed = expensive, External = cheap." That is wrong. Volume type itself is not the primary cost driver. Real drivers are Azure Storage capacity, storage transactions, data transfer, compute, document processing (OCR, extraction, chunking, embedding), and AI processing. Compute spent processing large PDFs can far exceed the cost of simply storing them.

14) Storage footprint example

Assume 12 PDFs per client at roughly 5 MB each. That is 60 MB per client. For 1,000 clients you are looking at about 60 GB. For 10,000 clients, about 600 GB. That is only the original PDF footprint before derived data. The underlying Azure storage bill still depends on the storage account's configuration and actual usage, not on whether the Unity Catalog object is labelled Managed or External.

15) Bad vs better processing architecture

```
BAD:    question → open PDF → OCR → extract → chunk → embed → answer
        (repeated for every question — wasteful compute and storage ops)

BETTER: PDF → extract → clean text → chunk → embed/index   (done once)
        question → agent → retrieve relevant chunks → answer
```

Process once, serve many times. That is the efficient pattern.

16) Security pattern

Both Managed and External Volumes can be governed through Unity Catalog. With External storage you must pay extra attention to the chain: Azure identity → Storage Credential → External Location → Volume permissions. Do not give users uncontrolled direct access to the underlying ADLS path — that bypasses the governance boundary you are trying to establish in Databricks.

```
Intended:  User → Unity Catalog → Volume → File
Avoid:     User → Direct ADLS → File
```

Grant access to the Volume. Never expose the raw External Location.

17) Volume vs Vector Search vs DBFS

A Volume is not a vector database. A Volume stores and governs files. Vector Search retrieves semantically relevant chunks. The full flow is:

```
PDF → Volume → extract → chunk → embedding → Vector Search → AgentBricks
```

Also do not confuse Volumes with older DBFS and DBFS mounts. For a new Unity Catalog architecture the modern thinking is:

```
Unity Catalog → Volumes → governed file access
```

18) Overall use-case architecture

```
                    DATABRICKS USE CASE
                           │
             ┌─────────────┴─────────────┐
       STRUCTURED DATA             UNSTRUCTURED DATA
             │                           │
          BRONZE                       ADLS
             │                           │
          SILVER                         ▼
             │                    EXTERNAL VOLUME (PDFs)
           GOLD                          │
             └─────────────┬─────────────┘
                           ▼
                       PLATINUM (AI Context Layer)
                           ▼
                      AgentBricks
```

In one sentence: tables manage structured business data; Volumes govern file-based data; External Volumes connect Unity Catalog to enterprise-managed ADLS; Platinum turns governed structured and unstructured data into AI-ready context; AgentBricks consumes that controlled context.

The Volume holds the original PDF. Platinum holds the AI-ready context after extraction, chunking, and metadata enrichment. Platinum is the bridge between unstructured source and the agent.

19) Interview-style answers to remember

**Why not store PDFs as tables?**
PDFs are unstructured files, so we use a Unity Catalog Volume for governed file storage. We maintain document metadata and extracted/chunked representations in tables, while retaining the original PDF as the source document.

**Why External Volume?**
The original documents reside in an ADLS Gen2 repository that we want to keep as the authoritative storage location. We register the ADLS path through a Unity Catalog External Location and expose it through an External Volume, giving Databricks governed access without unnecessarily relocating the files.

**Why not Managed Volume?**
Managed Volume would be appropriate if Databricks were responsible for the document storage lifecycle. Because our document repository is intentionally maintained in ADLS as an externally managed location, External Volume is more appropriate.

**Which one is cheaper?**
Neither volume type inherently has a simple lower storage price. The underlying ADLS capacity, transaction volume, network transfer, and document-processing compute drive most of the cost. Managed vs External is primarily a storage ownership, lifecycle, and governance decision.

20) 10 things to remember

1. Volume = governed file storage, not a table.
2. Tables → structured data; Volumes → files.
3. Managed Volume = Unity Catalog controls the storage location and lifecycle.
4. External Volume = you control the underlying cloud storage.
5. External Volume normally needs Storage Credential + External Location.
6. External does NOT mean ungoverned.
7. Volume type itself is not the main cost driver.
8. ADLS storage + transactions + compute + processing drive the actual cost.
9. One Volume → many client folders; never one Volume per client.
10. For our use case: PDFs → External Volume → processing → Platinum → AgentBricks.
