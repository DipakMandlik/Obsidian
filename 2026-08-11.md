2) ADLS Storage Setup with Databricks :
	1) Approach : Entirely via Azure Portal + Databricks UI (no SQL). Used an **External Volume on ADLS Gen2** since PDFs must remain in our own ADLS location.
	2) Sequence followed : ADLS folder → Azure identity/access → Databricks Storage Credential → Databricks External Location → Databricks External Volume → client folders → PDFs.
	3) Target architecture :
		- 1 ADLS document repository → 1 External Location → 1 External Volume → many client folders (not one volume per client).
		- Structure: `databricks-use-case` (container) → `documents/` → `CLIENT_001/`, `CLIENT_002/`, ... → per-client subfolders `financial/`, `legal/`, `compliance/`, `supporting/` with meaningfully named PDFs.
	4) Step 1 — Created ADLS Gen2 storage : Verified **Hierarchical namespace = Enabled** on the storage account.
	5) Step 2 — Created container : `databricks-use-case`, access level **Private**.
	6) Step 3 — Created document folder : `documents` (root of the external volume).
	7) Step 4 — Created folder structure : Client folders (`CLIENT_001`, `CLIENT_002`, ...) each with `financial/`, `legal/`, `compliance/`, `supporting/` subfolders instead of generic `document_01.pdf` naming.
	8) Step 5 — Created Access Connector for Azure Databricks : Name `ac-databricks-use-case`, same subscription/resource group/region as the Databricks workspace.
	9) Step 6 — Granted the Access Connector permission on ADLS : Storage Account → IAM → Add role assignment → **Storage Blob Data Contributor** → assigned to Managed Identity `ac-databricks-use-case`.
	10) Step 7 — Opened Databricks Catalog Explorer : Catalog → Connect → Credentials.
	11) Step 8 — Created Storage Credential : Type **Azure Managed Identity**, name `cred_databricks_use_case_adls`, linked to `ac-databricks-use-case`. (Unity Catalog → Storage Credential → Managed Identity → ADLS Gen2)
	12) Step 9 — Created External Location : Catalog → Connect → External Locations → name `extloc_databricks_use_case_documents`, storage type **Azure**, URL `abfss://databricks-use-case@<storage-account>.dfs.core.windows.net/documents/`, credential `cred_databricks_use_case_adls`.
	13) Step 10 — Validated the External Location : Confirmed URL, credential, and status = accessible before proceeding (stop and fix identity/RBAC/URL/privileges if it fails here).
	14) Step 11 — Created the External Volume : Catalog `databricks_use_case` → schema `documents` (created if missing) → Create Volume → name `client_documents`, type **External**, location = same ADLS `documents/` path.
	15) Result — Governed access path : Physical `abfss://databricks-use-case@<storage-account>.dfs.core.windows.net/documents/` is now exposed as `/Volumes/databricks_use_case/documents/client_documents/`, containing all client folders/subfolders. Data-processing jobs reference this Volume path instead of the raw ADLS URI.
	16) Permission model applied :
		- Data Engineering group → READ VOLUME + WRITE VOLUME.
		- AI/Agent application identity → READ VOLUME only (no delete/overwrite).
		- Business users → no direct Volume access; interact via the application/agent.
		- Users/agents are granted access to the **Volume**, never the raw External Location.
	17) Avoided anti-pattern : Did **not** create one volume per client (e.g. `Volume_CLIENT_001`, `Volume_CLIENT_002`, ...). Kept **one volume** with client ID as a metadata/filtering attribute (`document_id`, `client_id`, `document_type`, `document_path`, `document_date`, `processing_status`, `classification`).
	18) Key takeaway — four objects to remember :
		- **ADLS folder** = where PDFs physically live.
		- **Storage Credential** = how Unity Catalog authenticates to Azure.
		- **External Location** = which ADLS path Unity Catalog governs.
		- **External Volume** = the governed file-access interface used by Databricks workloads.
		- Never skip directly from ADLS → Volume; always go ADLS → Storage Credential → External Location → External Volume.
