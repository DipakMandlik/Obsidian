Snowflake Dynamic Table :
				1) A dynamic table **materializes the results of a SELECT query and keeps them up to date automatically**
				2) Instead of writing custom orchestration code, you simply specify the target query and a desired "target lag," and Snowflake tracks dependencies and schedules data refreshes on your behalf

	** Demo :
					1) Simply a normal snowflake table is being created or we can called it as Dynamic Table :
    Query : 
							CREATE DATABASE IF NOT EXISTS dt_demo;
							CREATE SCHEMA IF NOT EXISTS dt_demo.raw;
							CREATE SCHEMA IF NOT EXISTS dt_demo.analytics;

							-- Step 2: Create the source table
							CREATE OR REPLACE TABLE dt_demo.raw.transactions (
							    transaction_id   INT AUTOINCREMENT,
							    product_id       VARCHAR(10),
							    quantity         INT,
							    amount           DECIMAL(10,2),
								    sold_at          TIMESTAMP DEFAULT  CURRENT_TIMESTAMP() );

1) Inserting records for the demo 
							INSERT INTO dt_demo.raw.transactions (product_id, quantity, amount, sold_at)
    VALUES
    ('P001', 2, 19.99, DATEADD('hour', -3, CURRENT_TIMESTAMP())),
    ('P002', 1, 49.99, DATEADD('hour', -2, CURRENT_TIMESTAMP())),
    ('P003', 5, 49.95, DATEADD('hour', -1, CURRENT_TIMESTAMP())),
    ('P004', 3, 89.97, DATEADD('minute', -30, CURRENT_TIMESTAMP())),
    ('P005', 4, 199.96, DATEADD('minute', -10, CURRENT_TIMESTAMP())),
    ('P006', 1, 29.99, CURRENT_TIMESTAMP());

2) Create the first dynamic table (1-minute lag)
	  CREATE OR REPLACE DYNAMIC TABLE dt_demo.analytics.sales_summary
	  TARGET_LAG = '1 minute'
	  WAREHOUSE = COMPUTE_WH
		AS
		SELECT
		    DATE_TRUNC('day', sold_at) AS sale_date,
		    product_id,
		    SUM(quantity)              AS total_quantity,
		    SUM(amount)                AS total_amount
		FROM dt_demo.raw.transactions
		GROUP BY 1, 2;


3) Create a downstream dynamic table (also 1-minute lag)
		CREATE OR REPLACE DYNAMIC TABLE dt_demo.analytics.top_products
		 TARGET_LAG = '1 minute'
		  WAREHOUSE = COMPUTE_WH
		  REFRESH_MODE=AUTO|FULL|INCRMENTAL|ADAPTIVE
		  INITIALIZE=ON CREATE | ON SCHEDULE
			AS
				SELECT
				    sale_date,
				    product_id,
				    total_amount,
				    RANK() OVER (PARTITION BY sale_date ORDER BY total_amount DESC) AS daily_rank
				FROM dt_demo.analytics.sales_summary
				WHERE total_amount > 0
				QUALIFY daily_rank <= 10;
4) Now we can check first time the data is loaded properlly or not okay 
5) Insert new rows to see the automatic refresh in action
	INSERT INTO dt_demo.raw.transactions (product_id, quantity, amount)
	VALUES ('P009', 10, 299.90), ('P001', 7, 69.93);
6) SELECT * FROM dt_demo.raw.transactions;

	-- Step 8: After ~1 minute, query again to confirm the refresh picked up new data
	SELECT * FROM dt_demo.analytics.sales_summary ORDER BY sale_date, product_id;
	SELECT * FROM dt_demo.analytics.top_products ORDER BY sale_date, daily_rank;

**How Dynamic Tables Stay Updated** When you create a dynamic table, Snowflake parses the query to identify the base tables it reads from. Snowflake then continuously monitors these base tables for changes. When changes are detected, it computes the new results and applies them atomically, ensuring that users never see a partial or incomplete refresh


**Key Concepts** : 
			1) **Target Lag:** This setting defines **how fresh the data must be**. For example, a target lag of 10 minutes means Snowflake attempts to keep the data no more than 10 minutes behind the base tables. You can also set `TARGET_LAG = DOWNSTREAM` for intermediate tables, which tells them to refresh only when a downstream dependent table requires fresh data.
			2) - **Refresh Modes:** You can control how the table updates its data.
			    - **INCREMENTAL:** Processes only the rows that have changed since the last refresh.
			    - **FULL:** Refreshes the entire result set.
			    - **AUTO:** Allows Snowflake to choose the optimal mode based on the query definition.
			    - **ADAPTIVE:** Uses incremental refresh by default but will automatically reinitialize if it detects large upstream changes.
			    - **CUSTOM_INCREMENTAL:** Allows you to define custom refresh logic using DML statements.
			- **Pipelines and Automated Scheduling:** When dynamic tables read from one another, **Snowflake automatically infers the dependency graph** and treats them as a pipeline. It picks a consistent snapshot timestamp and refreshes the tables in dependency order so that downstream tables always reflect a consistent view of their upstream inputs. If preferred, you can set `SCHEDULER = DISABLE` to trigger refreshes manually or via an external tool like dbt or Airflow.

**Cost Structure** Dynamic tables incur costs across three main categories:

1. **Warehouse Compute:** The virtual warehouse resources used to run each refresh query.
2. **Cloud Services:** Covers the background tasks of compiling the query, tracking dependencies, and coordinating refreshes. Shorter target lags require more scheduling work and will increase these costs.
3. **Storage:** The cost of adding, replacing, or removing micro-partitions during refreshes, as well as Time Travel retention

 The costs associated with Snowflake dynamic tables are broken down into three main categories:

**1. Warehouse Compute Costs** This covers the compute resources used by the virtual warehouse to execute each refresh query. The primary factors that drive these costs include:

- **Warehouse size:** Larger warehouses cost more credits per hour.
- **Refresh frequency:** How often the dynamic table refreshes based on its target lag.
- **Query complexity and data volume:** Heavier transformations and larger datasets require more compute time to process.

**2. Cloud Services Costs** These costs are incurred from the background tasks Snowflake performs to manage the dynamic tables. This includes compiling the refresh queries, tracking dependencies across pipelines, monitoring base tables for changes, and coordinating the actual refreshes. The key drivers for Cloud Services costs are:

- **Target lag:** A shorter target lag means the system has to perform more scheduling work and checks, which increases costs.
- **Pipeline complexity:** The number of dynamic tables, the depth of the pipeline, and the complexity of the queries all contribute to higher cloud services usage.

**3. Storage Costs** Storage costs are incurred as data is physically materialized. Whenever a refresh occurs, Snowflake adds, replaces, or removes micro-partitions within the table. The main factors impacting storage costs include:

- **Table size and refresh volume:** The overall size of the dynamic table and the number of micro-partitions modified during each refresh.
- **Time Travel retention:** Retaining historical data for Time Travel (which can be configured up to 90 days for permanent tables in Enterprise editions) requires additional storage, which will be reflected in your monthly storage charges.

Scenarios: When Dynamic Tables are Beneficial (Advantages)

Dynamic tables are highly advantageous when you want to build a declarative data pipeline without writing custom orchestration code. They are ideal in the following scenarios:

- **Moving to Near-Real-Time:** If you want to transition an existing pipeline from slow batch processing to near-real-time freshness, you can do so easily by just adjusting the single `TARGET_LAG` parameter.
- **SQL-Based Transformations:** When your entire transformation logic can be expressed purely as a SQL `SELECT` statement.
- **Complex Multi-Step Pipelines:** They are highly beneficial when you need to build pipelines involving joins, aggregations, or window functions. Because Snowflake automatically infers the dependency graph, downstream tables will always see a consistent, synchronized snapshot of their upstream inputs without you having to manually script the execution order.

Scenarios: When Dynamic Tables are NOT Beneficial (Disadvantages)

You should avoid using dynamic tables in scenarios where their limitations conflict with your business requirements. They are not recommended if:

- **Ultra-Low Latency is Required:** Dynamic tables cannot support workloads that require data to be fresher than 60 seconds, which is the absolute minimum allowed target lag.
- **Strict Timing is Needed:** If your business requires strictly guaranteed refresh timing, dynamic tables are not suitable because the actual lag can exceed your target if a refresh query takes longer than expected to run.
- **Unsupported Logic:** You cannot use dynamic tables if your pipeline requires stored procedures, external functions, or User-Defined Table Functions (UDTFs) outside of lateral joins, as these are not supported in dynamic table definitions
