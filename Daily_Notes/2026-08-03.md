what is apache iceberg ?
			**Apache Iceberg is an open table format for large analytical datasets.**

Notice the wording carefully:

- It is **not** a database.
- It is **not** a data warehouse.
- It is **not** a storage service.
- It is a **table format**.

A table format defines **how data files and metadata are organized, tracked, and managed** inside object storage such as Amazon S3, Azure Data Lake Storage, or Google Cloud Storage.

	How it works:
	- Iceberg sits **between the storage layer and the query engine** (Spark, Trino, Flink, Snowflake, DuckDB...)
	- Unlike Hive tables (where the engine decides semantics), the **table format itself enforces correctness** — schema, partitions and file layout travel with the table, not with whoever wrote it
	- Mental model: **"git for your data table"**
		- Files on disk = blobs
		- Each commit = a new **snapshot** (a metadata pointer to a consistent set of files)
		- `version-1.metadata.json` → `version-2.metadata.json` → ... (a JSON catalog of table state)
		- Query any past snapshot (`time travel`), roll back errors — like `git checkout`

	Key capabilities:
	- **ACID transactions** — concurrent writers + readers, no partial reads, atomic commits
	- **Snapshot isolation / time travel** — every commit is a snapshot; query any past state, roll back bad writes
	- **Schema evolution** — add/drop/rename columns **without rewriting data**
	- **Hidden partitioning** — partitioning is metadata, not user-managed folders; engines auto-prune for you
	- **Multi-engine** — same table readable by Spark, Flink, Trino, Snowflake, DuckDB — no vendor lock-in

	Why it matters for Snowflake:
	- Snowflake's internal format is closed (only queryable in Snowflake). Iceberg = Snowflake's "open table" bridge to a lakehouse:
		- **Consumer**: read external Iceberg tables in your own S3/ADLS storage, not locked into Snowflake's format
		- **Producer**: write tables in open Iceberg format so other engines can read them (Snowflake Open Catalog = Iceberg catalog service)

	Real-world example:
	- **The problem**: A fintech company stores transactions in Snowflake (closed format) but ML engineers need the same data in Spark for fraud models, and auditors need historical point-in-time reads.
	- **The fix**: They create the table as an **Iceberg table in S3** via Snowflake. One write, and:
		- Snowflake analysts query it in SQL
		- ML team reads the *same* S3 files directly with Spark for training — no duplicate pipelines
		- Fraud incident on 2026-06-01 → auditors run `SELECT ... FOR VERSION AS OF '<snapshot>'` to see the exact table state at that moment (time travel)
		- Schema change (adding a `risk_score` column) is metadata-only — no `ALTER` rewrite of billions of rows
	- **Result**: one table, zero copies, shared by every engine, with a full audit history. That's the Iceberg value proposition.
